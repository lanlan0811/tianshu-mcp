# v0.9.3 — Codex 26.1002 适配修复版

> **Codex 适配器修复版**：Codex 桌面端升级到 **26.1002** 后，适配器连续暴露 **5 个缺陷**。
> 其中 3 个会让派单**完全无法进行**——最严重的一个会**假报成功**。
> 本版逐个修复，每个都带真机复现证据或回归锁。

**本版无破坏性变更、工具面不变（仍 8 个工具），升级无需改调用方。**

---

## 背景

Codex 从 **26.930** 升级到 **26.1002** 后，界面行为发生了几处关键变化，
而适配器的多处判据是按旧版本实测沉淀的，于是在新版上依次失效：

| 变化 | 旧假设 | 后果 |
|---|---|---|
| 重启后停在**既有会话**视图 | composer 总是已挂载 | 连接阶段超时，**走不到派单步骤** |
| `messageArea` 容器**包含** composer | 对话区文本即"已送达" | **假报发送成功** |
| 游离克隆体读 `innerText` 返回空壳 | 克隆是安全的采集手段 | 对话哈希恒定，**回复稳定判定失真** |
| 进程退出 → CDP `ECONNREFUSED` | 报 CDP 错误即可 | 报错指向**症状**而非真因 |

---

## 修复清单

### 1. 发送确认假成功（最严重）

`messageArea` 选择器命中的容器**把 composer 一起包住**：

```
MainContentSurface(y=96,h=680)
  └─ … └─ _ComposerLayoutRoot_(y=610)
           └─ div.ProseMirror          ← 输入框
```

于是「输入框里还留着任务书」被算作「对话区已出现该文本」→ 报
`指令已确认发送（对话区=true）`，**任务书根本没发出去**，后续轮询对着一个
不会变化的页面等到超时，残留文本还污染下一轮。

**修复**：在可见容器上做**节点级遍历**，整棵跳过 composer 组件节点。

### 2. 连接阶段的就绪判据顺序颠倒

`connectStableCodex` 原先只认 `chatInput` 作为就绪信号：

```ts
if (await candidate.exists("chatInput")) return candidate;   // ← 只认这一个
...
// 直到第 320 行才点「新对话」
if (gui.freshSession && !(await cdp.click("newChat"))) ...
```

但页面停在既有会话时 composer **并不挂载**（真机实测 `chatInput=0`，
而「新聊天」按钮可点）。于是重试到超时报「Codex 输入框尚未恢复」，
**根本走不到点「新对话」的那一步**——顺序颠倒。

**修复**：就绪判据放宽为「`chatInput` 已挂载 **或** `newChat` 可点」，
并在点击「新对话」后显式等待 composer 出现（新会话页的 composer 是**异步挂载**的），
等不到则明确报「点击新对话后输入框未出现」，不再以含糊超时收场。

### 3. 回复稳定判定失真（`conversationText` 恒定）

原实现用**游离克隆体**采集文本。而游离节点**没有布局**——Chromium 对它取
`innerText` 只返回空壳：

| | 真机实测 |
|---|---|
| 可见容器真实对话 | **605 字符** |
| 游离克隆体读到 | **4 字符**（`"输出内容"`） |

于是 `conversationText` 恒定、哈希恒定（三轮对话哈希全是 `87b0fa42c896`），
回复稳定判定完全失真。

同时 `[class*="Composer"]` 子串匹配会**误伤对话滚动容器**——
Tailwind 变体 `has-[[data-composer-expand-toggle]]` 也含该子串，29 个命中节点里
**包含整个 `thread-scroll-container`**。

**修复**：
- 节点级遍历 + `textContent`（不依赖布局，游离与在树内行为一致）
- 只跳过 composer **组件**节点（精确基名 `_ComposerLayoutRoot_` / `_ComposerLayoutBody_`）
- 叶子文本以**空串拼接**——用空格拼会把 `【tianshu:xxx】` 拆成两段，令 `seenMessage` 失效

**真机复验**：`conversationText` **4 → 428 字符**；哈希由恒定变为随内容变化；
模型工具条与档位条均不再污染。

### 4. 进程退出被误报为 CDP 断开

真机 kill 进程后 CDP 报 `ECONNREFUSED`——那是**结果**不是原因。
旧实现把它当作 CDP 断线处理，用户看到的排查方向是错的。

**修复**：新增 `diagnoseCdpLoss()`，两处断连出口（发送确认环 + 运行检测环）共用；
探测失败时按「进程仍在」**保守处理**，不误判为实例退出。

### 5. CDP 错误文案硬编码程序名

`TraeworkCdpClient` 被 **6 个**适配器复用
（traework / codex / kimicode / minimax / opendesign / qoder），
但错误文案硬编码了 TraeWork——其余 5 个适配器出错时会把用户引到**错误程序**。

**修复**：新增 `CdpClientOptions.appLabel`，各适配器传入自己的程序名。

## 已知问题

1. **新会话首轮偶发「发送未触发」**：Codex 26.1002 下，文本已键入但未触发发送，
   报 `send_unknown`（文本仍留在输入框、产物未生成）。
   该路径**不会重发**（重发风险高于误判），故如实报错而非假成功。
   下次将针对发送链路单独修复。
2. **模型选择器混入分组标题**：新版分组标题（如「默认/推荐模型集」）与真模型项
   同为 `role="menuitemradio"`，可能混入模型候选（真模型项有 `data-state`，标题没有）。
3. **`【tianshu】` 标记跨 span 时丢中间段**：已在叶子拼接处规避最常见形态，
   极端嵌套场景待后续处理。
